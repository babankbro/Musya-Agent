# Adaptive Agent Workflow Architecture

## Problem Statement
How might we build an agent workflow that handles ambiguous tasks autonomously, transparently exposes its plan as a modifiable state machine, and learns from user corrections to permanently improve its future performance?

## Recommended Direction
**The "Glass Box" Learning State Machine.** 
Instead of rigid predefined paths or a black-box chain of thought, the agent generates an ephemeral, explicit state machine for every complex task. The user can view, pause, rewind, and hot-swap steps in this machine mid-execution. 

Execution is governed by a **Confidence Threshold**: if confidence is high, the agent proceeds autonomously; if low, it pauses the state machine and asks for human intervention. Crucially, whenever the human intervenes or the agent encounters a failure, a background process extracts the learning and updates the agent's core rules or workflow definitions, ensuring the same mistake isn't repeated.

## Key Assumptions to Validate
- [ ] **Assumption 1 (User Desire):** Users actually want to interact with and modify the workflow state machine, rather than just wanting a "magic button" that works. *Test: Build a low-fidelity CLI or UI mockup of the state machine and observe user interaction.*
- [ ] **Assumption 2 (Confidence Calibration):** The LLM can accurately and consistently self-assess its confidence level to trigger human intervention appropriately. *Test: Run a benchmark of ambiguous tasks and measure the false-positive/false-negative rate of the confidence score.*
- [ ] **Assumption 3 (Safe Self-Modification):** The agent can update its own rules without introducing contradictions or catastrophic forgetting of previous rules. *Test: Implement a sandboxed rule-updater with an automated test suite that runs after every rule modification.*

## MVP Scope
**In Scope:**
- Generation of an explicit, multi-step plan (state machine) before execution.
- A simple `High/Low` confidence flag on each step.
- Execution pausing when confidence is `Low`, prompting the user for guidance.
- A feedback loop where user corrections during a paused state are saved to a local rule file or memory database.

**Out of Scope for MVP:**
- Complex UI for hot-swapping states (text-based pausing/editing is enough for V1).
- Rewinding execution state (requires complex environment state snapshotting).
- Automated A/B testing of self-modified rules.
- Parallel state machine execution.

## Not Doing (and Why)
- **Hardcoded Decision Trees:** They are too brittle for ambiguous tasks and require constant developer maintenance.
- **Silent Failures / Guessing:** We are explicitly choosing to stop and ask the user rather than guess when confidence is low, to build user trust.
- **Rewinding/Time-travel Debugging:** Snap-shotting entire filesystem/environment states to allow "rewinding" is technically massive and distracts from the core value of adaptability. We will focus on forward-correction first.

## Open Questions
- How do we quantify and standardize the "Confidence Score" across different types of models and tasks?
- What is the exact data schema for the explicit state machine so that both the agent and the human can read, parse, and modify it easily?
- Should self-modified rules be committed instantly, or placed in a staging area for human review?
