# 01.02 - Strategic Design & Roadmap

> **Strategic layer** for the Musya Agent project.
> - **Phase 1** (current) — RTI monolith with 10-agent Chat pipeline + Policy Brief + Short Chat
> - **Phase 2** — Modular 8-subsystem refactor enabling independent deployment and testing
> - **Phase 3** — Expansion to Mental Health and NCD domains

For current system state, see [[01.01 - System Architecture]].  
For the 8-subsystem modular design details, see [[01.04 - Subsystem Architecture]].

---

## 1. Three-Domain Product Vision

Musya Agent is designed to grow from a single-domain RTI (Road Traffic Injury) system into a **Thai public health intelligence platform** covering three linked domains:

| Domain | Status | Data sources |
|---|---|---|
| **RTI** — Road Traffic Injury | Phase 1 (current) | Accident DB, ThaiJO RTI articles, uploaded reports |
| **Mental Health** — Suicide prevention | Phase 2 target | Mental Health DB (requires safety guardrails) |
| **NCD / Nutrition** — Non-communicable disease | Phase 2 target | NCD DB (3-flow upstream/midstream/downstream) |

Each domain reuses the same **Shared Foundation** (Agents 1–4: Interpreter → Retrieval → SQL → Citation) and adds domain-specific analyst agents.

---

## 2. The Monolith Problem (Phase 1 Constraint)

The current Phase 1 architecture is a **monolith**: agents, tools, RAG, citation, and database access are tightly coupled.

```
orchestrator.py
  ├── imports every agent file directly
  ├── agents import tools directly
  ├── tools import db/pool directly
  ├── tools import rag/ directly
  └── citation agent imports schemas + db + apa_formatter directly
```

**Consequences:**
- Changing APA formatting requires edits across `citation agent`, `tools/common`, `rag/document_rag`, `routers/evidence`
- Adding a new data source (e.g. ThaiJO) required changes to retrieval agent, citation agent, schemas, config, and router
- Unit-testing is impractical due to deep import chains
- Agent 2 (Retrieval) has 10+ heterogeneous tools mixed together

## 3. Phase 2: 8-Subsystem Architecture

The proposed refactor splits the system into **8 independent subsystems** with clear boundaries and typed contracts:

```
API Gateway (FastAPI Routers)
  /api/chat  /api/policy-brief  /api/documents  /api/thaijo
       │
       ▼
Orchestration Subsystem
  (Router → Foundation Builder → Pipeline Executor → Response)
       │
  ┌────┴────┬──────────┬──────────┬──────────┐
  ▼         ▼          ▼          ▼          ▼
Document  APA &     ThaiJO    Database   (future)
RAG       Citation  Search    RAG        NLM Bridge
       │
  ┌────┴────┬──────────┐
  ▼         ▼          ▼
Report    Chart      NotebookLM
Engine    Builder    Bridge
       │
       ▼
Shared Infra (DB Pool · MinIO · Config · Logging)
```

See [[01.04 - Subsystem Architecture]] for complete module boundaries, typed contracts (`RetrievalResult`, `CitationContext`, `FinalReport`), and migration plan.

### Design goals

| Goal | Mechanism |
|---|---|
| Clear boundaries | Each subsystem exposes a typed Python interface only |
| Independent lifecycle | Subsystems can be developed, tested, and deployed separately |
| Plug-in data sources | New sources implement `RetrievalResult`; no changes elsewhere |
| Shared contract | All inter-subsystem communication via `contracts.py` Pydantic models |

## 4. Phase 2: Adaptive Agent Workflow

Alongside the subsystem refactor, the agent execution model evolves from fixed sequential chains to a **"Glass Box" Learning State Machine**:

- The agent generates an **explicit state machine** for every complex task (visible and modifiable by the user)
- A **Confidence Threshold** governs autonomous vs. human-in-the-loop execution
- User corrections feed back into a rule store, so mistakes are not repeated

See [[01.05 - Adaptive Agent Workflow]] for MVP scope, assumptions, and open questions.

## 5. Agentic AI & RAG Design Principles

The overarching design philosophy of the Musya AI RAG layer:

- **Hybrid RAG** — Document RAG (semantic) + Database RAG (structured SQL) + ThaiJO (academic articles)
- **Traceable evidence** — every sentence, table, and chart is linked to a registered evidence item (C-code range)
- **Agent-mediated access** — agents never touch raw tables; access is always through tool APIs with enforced boundaries
- **3-domain DB schema** — Accident DB / Mental Health DB / NCD DB share master data (geography, time, population, facility)

See [[01.06 - Agentic AI RAG Design]] for the full architecture diagram and DB schema.
