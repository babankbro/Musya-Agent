# การสร้างระบบ Document Canvas แบบ Google Docs / Gemini Canvas

การสร้างระบบแก้ไขเอกสาร (Rich Text Editor หรือ Canvas) ที่มีความสามารถระดับ Google Docs หรือ Canvas ของ Gemini (ที่ AI สามารถพิมพ์ตอบลงไปและผู้ใช้สามารถแก้ไขร่วมกันได้) เป็นโปรเจกต์ที่มีความซับซ้อนสูงมาก ต่างจากการใช้ `<textarea>` หรือ HTML `contenteditable` แบบธรรมดา

เอกสารบรรยาย 3 ส่วนนี้จะอธิบายถึงสถาปัตยกรรม (Architecture) เทคโนโลยีที่จำเป็น และขั้นตอนการนำ AI มาเชื่อมต่อให้ทำงานร่วมกันได้อย่างสมบูรณ์

---

## หน้าที่ 1: สถาปัตยกรรมหลักและแนวคิดพื้นฐาน (Core Architecture & Concepts)

ในการสร้าง Canvas ที่แก้ไขได้แบบเรียลไทม์ เราไม่สามารถเก็บข้อมูลเป็นเพียง "ข้อความ HTML" ยาวๆ ได้ เพราะเมื่อมีการแก้ไขพร้อมกัน (เช่น AI กำลังพิมพ์ และผู้ใช้ก็กำลังพิมพ์แทรก) HTML จะพังและข้อมูลจะสูญหาย สถาปัตยกรรมจึงต้องออกแบบเป็น **Block-based** หรือ **Tree-based Document Model**

### 1. Document Model (โครงสร้างข้อมูล)
เอกสารจะไม่ถูกเก็บเป็น String (เช่น `<p>Hello <b>world</b></p>`) แต่จะถูกแปลงเป็น JSON Tree (Abstract Syntax Tree) หรือโครงสร้างแบบ Block:
```json
{
  "type": "doc",
  "content": [
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "Hello " },
        { "type": "text", "marks": [{"type": "bold"}], "text": "world" }
      ]
    }
  ]
}
```
**ทำไมต้องใช้ JSON?** เพราะมันช่วยให้การคำนวณตำแหน่งเคอร์เซอร์ (Cursor) และการแทรกข้อความทำได้แม่นยำทางคณิตศาสตร์ เมื่อ AI ส่งข้อความมาทีละตัวอักษร (Streaming) ระบบจะรู้แน่ชัดว่าจะต้องแทรก node ใหม่อยู่ตรงตำแหน่งไหนของ Tree

### 2. The Editor Engine (ตัวจัดการการพิมพ์)
การพึ่งพาฟีเจอร์ `contenteditable` ของเบราว์เซอร์โดยตรง (แบบโปรแกรมสมัยเก่า) จะทำให้เกิดบั๊กมหาศาล เพราะแต่ละเบราว์เซอร์ (Chrome, Safari, Firefox) จัดการการกด Enter หรือ Backspace ไม่เหมือนกัน 
ระบบ Canvas สมัยใหม่จะใช้ Engine ที่ **ดักจับเหตุการณ์ (Intercept Events)** ทุกครั้งที่กดคีย์บอร์ด จากนั้น Engine จะคำนวณโครงสร้าง JSON ใหม่ แล้วสั่งวาดหน้าจอ (Render) ใหม่ด้วยตัวเองทั้งหมด เรียกว่าสถาปัตยกรรมแบบ **"Controlled Editor"**

### 3. State Management
ในระบบแบบ Gemini Canvas จะต้องแบ่ง State ออกเป็น 2 ส่วน:
*   **Editor State:** เก็บโครงสร้างเอกสาร ตำแหน่งเคอร์เซอร์ และไฮไลต์
*   **AI State:** สถานะว่า AI กำลังคิด กำลังพิมพ์ (Streaming) หรือพิมพ์เสร็จแล้ว รวมถึงประวัติ Prompt ที่ทำให้เกิดเอกสารนี้

## หน้าที่ 2: เทคโนโลยีสำหรับการทำงานร่วมกัน (Collaboration & Real-time Sync)

ความท้าทายที่สุดของ Canvas คือการทำให้ผู้ใช้แก้ไขพร้อมกับ AI หรือพร้อมกับเพื่อนร่วมงานคนอื่นได้โดยข้อความไม่ทับซ้อนกัน

### 1. เทคโนโลยี CRDT (Conflict-free Replicated Data Type)
หากผู้ใช้พิมพ์คำว่า "ก" ที่บรรทัดแรก และ AI พิมพ์คำว่า "ข" ที่บรรทัดสุดท้ายในเวลาเสี้ยววินาทีเดียวกัน ระบบเซิร์ฟเวอร์แบบเดิม (ใช้ Database ปกติ) จะงงว่าควรบันทึกเอกสารของใคร 
**CRDT** คืออัลกอริทึมคณิตศาสตร์ที่แก้ปัญหานี้ โดยมันจะมองการพิมพ์ทุกตัวอักษรเป็น "Operation" (เช่น แทรกตัว 'A' ที่ตำแหน่ง 5) CRDT จะรับประกันว่าไม่ว่า Operation จะเดินทางมาถึงเซิร์ฟเวอร์ช้าหรือเร็ว หรือสลับลำดับกัน เมื่อรวมกันแล้วทุกคนจะเห็นเอกสารหน้าตาเหมือนกัน 100% เสมอ
*   **ไลบรารียอดนิยมสำหรับ CRDT:** `Yjs`, `Automerge`

### 2. เฟรมเวิร์กสำหรับสร้าง Editor (Rich Text Frameworks)
คุณไม่จำเป็นต้องสร้าง Editor Engine เองตั้งแต่ศูนย์ (ซึ่งใช้เวลาหลายปี) ปัจจุบันมี Open-source Frameworks ที่บริษัทยักษ์ใหญ่ใช้เป็นรากฐาน:
*   **ProseMirror:** (ถูกใช้ใน New York Times, Atlassian) มีความยืดหยุ่นสูงสุด นิยมใช้ทำระบบที่ซับซ้อนมาก
*   **Lexical (โดย Meta/Facebook):** เฟรมเวิร์กยุคใหม่ที่เน้นประสิทธิภาพและทำงานเข้ากับ React ได้ดีมาก
*   **Tiptap:** สร้างครอบ ProseMirror อีกที ใช้งานง่ายมาก มี Extension ให้ใช้เยอะ (แนะนำให้เริ่มต้นด้วยตัวนี้)
*   **Quill.js:** ใช้งานง่าย แต่ปรับแต่งโครงสร้างระดับลึกได้ยากกว่า 3 ตัวแรก

### 3. การเชื่อมต่อข้อมูล (Transport Layer)
เพื่อความเรียลไทม์ เราไม่สามารถใช้ HTTP REST API ทั่วไปได้ ต้องเปลี่ยนมาใช้เทคโนโลยีการส่งข้อมูลแบบสองทาง:
*   **WebSockets:** สำหรับเชื่อมต่อ Yjs ระหว่างหน้าเว็บและเซิร์ฟเวอร์ (Node.js/Python) เพื่อ Sync ตำแหน่งเคอร์เซอร์และการพิมพ์
*   **Server-Sent Events (SSE):** เหมาะมากสำหรับฝั่ง AI RAG (เช่น Musya) เวลาที่ส่งข้อความจาก LLM กลับมาที่เบราว์เซอร์ทีละ Token

## หน้าที่ 3: การนำ AI มาผนวกกับ Canvas (AI Integration & Advanced Features)

ในระบบแบบ Gemini Canvas ตัว AI ไม่ได้แยกเป็นแค่ Chatbot ด้านข้าง แต่มันสามารถ "เข้าสิง" เอกสารและแก้ไขเอกสารแทนเราได้

### 1. AI Streaming เข้าสู่ Editor โดยตรง
เมื่อ AI สร้างเนื้อหา แทนที่จะนำเนื้อหาทั้งหมดมาแปะทับ (ซึ่งจะทำให้ผู้ใช้สะดุดและแก้ไขระหว่างนั้นไม่ได้) ระบบจะต้องแปลง AI Stream (จาก SSE) ให้กลายเป็น "คำสั่งพิมพ์ (Text Insertions)" ทีละตัวอักษรหรือทีละคำ เสมือนว่ามีบอทกำลังนั่งกดคีย์บอร์ดอยู่ในเอกสาร
*   **ขั้นตอน:** `Gemini Stream` -> `Backend Parser` -> `WebSockets/SSE` -> `Yjs Update (Apply Delta)` -> `Editor Re-render`

### 2. Inline AI Assistants (ผู้ช่วยแบบคลุมดำ)
ฟีเจอร์เด่นของ Canvas คือการที่ผู้ใช้สามารถ **ไฮไลต์คลุมดำ (Select)** ข้อความ แล้วสั่ง "สรุป", "ขยายความ", หรือ "แปลภาษา"
*   **วิธีทำ:** เมื่อผู้ใช้คลุมดำ ระบบจะดึงพิกัด (Range) จาก Editor State พร้อมกับดึงข้อความรอบๆ (Context) ส่งไปให้ Backend (เช่น RAG ของ Musya) Backend จะตอบกลับมาเป็นข้อความที่ปรับปรุงแล้ว จากนั้นใช้คำสั่ง `replaceRange` ของ Editor ทับเฉพาะจุดที่เลือกไว้ พร้อมกับมี Transition Animation สวยๆ

### 3. การทำ Versioning และ Artifacts
แบบเดียวกับที่คุณใช้งาน Chat กับ AI ในปัจจุบัน การแก้เอกสารโดย AI แต่ละครั้งควรถูกบันทึกเป็น "Version" เพื่อให้ผู้ใช้สามารถกด Undo (ย้อนกลับ) หรือเปรียบเทียบ (Diff) ระหว่างก่อนและหลังที่ AI แก้ไขได้
*   **Snapshots:** บันทึก JSON Tree ของเอกสารลง Database (เช่น PostgreSQL ใน Musya) ทุกครั้งที่ AI ทำงานเสร็จ
*   **Diff UI:** สร้างระบบไฮไลต์สีเขียว (เพิ่ม) และสีแดง (ลบ) เพื่อแสดงให้เห็นว่า AI ปรับเปลี่ยนคำตรงไหนบ้าง

### สรุป Technology Stack สำหรับสร้าง Canvas แบบ Gemini
*   **Frontend UI:** React.js / Next.js
*   **Editor Core:** Tiptap หรือ Lexical (จัดการ Rich Text)
*   **Collaboration:** Yjs (จัดการแก้ไขพร้อมกันและ Conflict)
*   **Backend Sync:** Hocuspocus (Yjs WebSockets server) หรือปรับปรุง FastAPI ของ Musya ให้รองรับ WebSockets
*   **AI Backend:** LangChain / CrewAI ส่งข้อมูลแบบ Streaming (SSE)
*   **Database:** PostgreSQL (เก็บ Document Snapshots) + Redis (Pub/Sub สำหรับ Sync ข้อมูลข้าม Server)
